## 🖥️ Demo 1：AI 服务器巡检（2 分钟）

### 准备

- 浏览器已打开：`http://localhost:8000`
- 已登录账号

### 操作

**输入**：
```
检查服务器状态
```

### 展示要点

1. **输入后** → 指向 Agent Trace 面板：
   > "注意看右边的执行轨迹，Agent 正在拆解你的需求。"

2. **Agent 调用工具时**：
   > "现在 Agent 调用了 `server_health()` 工具，正在采集 CPU、内存、磁盘数据。"

3. **报告生成**：
   > "数据采集完成后送到 LLM 分析，生成结构化的巡检报告。"
   > "比如这里磁盘 C: 使用率到 90% 了，Agent 会自动标记为风险项并给出建议。"

### 面试官可能问

| 问题 | 回答要点 |
|------|---------|
| 为什么用 LLM 做巡检？ | 传统巡检需要写脚本、配置告警阈值，LLM 可以理解自然语言指令、生成可读报告、结合知识库给出解决方案 |
| 工具调用会失败吗？ | 有完善的错误处理机制，工具超时、网络失败等异常会被捕获并通知 LLM 重试或降级 |

## ☸️ Demo 2：Kubernetes 故障诊断（2.5 分钟）

### 操作

**输入**：
```
帮我诊断 production 命名空间的异常 Pod
```

### 展示要点

1. **Agent 多步骤推理**：
   > "注意看 Trace 面板，Agent 自动分解了任务——先获取 Pod 列表，再查看异常 Pod 的事件，最后取日志。"

2. **工具链执行**：
   > "Agent 调用了三个 kubectl 工具：`get_pods` → `describe_pod` → `logs`，完全自主决策，不需要人指导。"

3. **诊断结果**：
   > "LLM 综合分析后给出了根因判断——比如 OOMKilled 表示内存超限，CrashLoopBackOff 表示应用启动失败，还附带了解决步骤。"

### 面试话术

> "这是项目最核心的能力——Agent 不仅会调工具，还会根据上下文自主选择工具的执行顺序。比如发现 Pod 异常，它会自动从 get_pods 开始诊断链路，而不会盲目执行所有工具，这背后是 LangGraph 的状态图编排。"

## 📚 Demo 3：RAG 知识库（2.5 分钟）

### 准备

已准备好一份 K8s 故障文档。

### 操作

1. **上传文档**（提前做或现场演示）：
   > "先上传一份 Kubernetes 故障排查手册到知识库。"

2. **提问**：
   ```
   Pod 为什么会 CrashLoopBackOff？怎么排查？
   ```

### 展示要点

1. **知识检索过程**：
   > "注意看 Agent 的执行轨迹——在执行 LLM 之前，Agent 先从知识库中检索了相关文档片段。"

2. **RAG 增强回答**：
   > "对比一下：如果不加知识库，LLM 只能基于训练知识回答，比较通用。加了 RAG 后，回答会更具体、更贴近我们内部的操作规范。"

### 面试话术

> "RAG 是这个项目的关键设计之一。企业运维中大量知识是沉淀在内部文档中的，比如故障处理 SOP、系统部署手册。RAG 让这些静态文档变成了 Agent 可以实时引用的动态知识，解决了一般 LLM 的知识时效性和定制化问题。"

### 面试官可能问

| 问题 | 回答要点 |
|------|---------|
| Embedding 用的是什么？ | 目前使用 DeepSeek/SiliconFlow 提供的 Embedding API，内置降级方案（固定向量） |
| 为什么不用 Fine-tuning？ | 运维知识更新频繁，Fine-tuning 成本高、周期长；RAG 可以实时更新文档库，更灵活 |
| 如何避免幻觉？ | RAG 提供的上下文和 Agent 系统提示的约束，以及 LLM 的搜索结果引用机制 |

## 📝 总结（1.5 分钟）

### 架构设计

> "整个项目的架构分为三层：
>
> **第一层是用户交互层**：React Web 控制台 + WebSocket 实时轨迹
>
> **第二层是 Agent 引擎层**：FastAPI + LangGraph 编排，集成了短期记忆、长期记忆、RAG 知识库三个增强模块
>
> **第三层是工具执行层**：SSH、Docker、Kubernetes 三种工具，通过统一接口注册到 Agent"

### 技术挑战

> "开发中主要遇到几个挑战：
>
> **1. LLM 工具调用的可靠性**：需要精心设计 System Prompt 和工具描述，让 LLM 准确理解每个工具的用途和参数
>
> **2. RAG 知识的有效注入**：文档分割大小、重叠窗口、检索 top_k 都需要调参实验，确保知识既能完整又不过度冗余
>
> **3. 多步骤任务编排**：使用 LangGraph 的状态图设计，确保 Agent 在复杂的多步任务中不会陷入死循环"

### 个人角色

> "这个项目从架构设计、代码实现、测试验证到文档包装，全部由我独立完成。过程中涉及了 FastAPI、LangGraph、React、Docker、K8s、Prometheus 等多个技术领域。"

## 🎯 Bonus：面试官可能追问的问题

| 问题 | 回答方向 |
|------|---------|
| 为什么选择 LangGraph？ | 相比 LangChain 的 Chain，LangGraph 支持循环、分支、状态持久化，更适合多步骤工具调用的场景 |
| 如何保证 Agent 不乱执行危险操作？ | K8s 双开关设计（enable + allow_restart）、SSH 命令黑名单、操作审计日志记录每一步执行 |
| 生产环境可以部署吗？ | 开发环境 SQLite + 单进程，生产环境切换 PostgreSQL + Gunicorn + Docker 编排 |
| 如果 LLM API 挂了怎么办？ | 内置降级方案：Embedding 失败用固定向量，LLM 失败返回错误提示并建议检查 API Key |
| 前端为什么不用 Next.js？ | 项目以 API 为中心，前端是控制台角色，SPA + Nginx 反向代理更简洁、更容易部署 |
