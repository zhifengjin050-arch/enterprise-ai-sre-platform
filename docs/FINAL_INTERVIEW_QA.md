## 一、Agent 相关问题（5 问）

### Q1：为什么不用普通 ChatGPT，而要自己开发 Agent？

**回答方向**：定制化 + 工具调用 + 数据安全

**答案要点**：

| 维度 | ChatGPT | 本项目 Agent |
|------|---------|-------------|
| **知识范围** | 通用知识，无企业内网数据 | RAG 注入企业运维文档 |
| **工具调用** | 无法执行 SSH/Docker/kubectl | 11 种运维工具实时调用 |
| **记忆能力** | 短期上下文有限 | 短期（对话历史）+ 长期（历史故障） |
| **数据安全** | 数据经过第三方 | 私有部署，数据不出内网 |
| **定制化** | 无法控制回答风格 | 可定制 System Prompt + 工具集 |

> **ChatGPT 适合通用问答，企业运维需要的是能理解内部系统、能执行操作、能记住历史经验的私有 Agent。本项目通过 LangGraph 编排 + RAG 知识库 + 工具注册机制实现了这一切。**

---

### Q2：Agent 如何选择要调用哪个工具？

**回答方向**：LLM Function Calling + 工具描述 + 路由逻辑

**答案要点**：

1. **工具注册**：每个工具注册时提供 `name`、`description`、`parameters`（JSON Schema）
2. **LLM 决定**：将工具列表作为 function calling 参数传给 LLM，LLM 根据用户意图和工具描述自动选择
3. **示例**：
   - 用户问"检查服务器状态" → LLM 选择 `server_health`
   - 用户问"看看容器日志" → LLM 选择 `docker_logs`
   - 用户问"Pod 为什么重启" → LLM 选择 `kubectl_describe_pod` + `kubectl_logs`
4. **LangGraph 路由**：Agent Node 判断 LLM 输出是否包含 tool_calls，有则进入 Tools Node 执行，无则直接返回

---

### Q3：如何避免 Agent 执行错误或危险操作？

**回答方向**：多层安全防护

**答案要点**：

| 安全层 | 措施 |
|--------|------|
| **K8s 双开关** | `KUBERNETES_ENABLED=false`（默认禁用）+ `KUBERNETES_ALLOW_RESTART=false`（重启操作独立开关） |
| **SSH 命令黑名单** | 禁止 rm -rf、dd、mkfs 等危险命令 |
| **工具超时控制** | SSH 连接超时 10s，命令执行超时 30s |
| **操作审计日志** | 所有 Agent 执行记录存入 agent_executions 表，tools_called 字段 JSON 记录完整调用链路 |
| **速率限制** | API 层 60 req/min，防止 Agent 高频调用 |
| **JWT + RBAC** | viewer 角色不可执行写操作 |

---

### Q4：Agent 执行多步骤任务时，如果某一步失败怎么办？

**回答方向**：错误捕获 + LLM 重试 + 降级

**答案要点**：

1. **工具执行异常捕获**：每个工具调用包裹 try-except，异常信息作为结果返回 LLM
2. **LLM 自主决策**：LLM 收到失败结果后，可以选择重试、换工具或给出错误报告
3. **LangGraph 循环**：工具结果送回 LLM 节点重新处理，形成闭环
4. **防止死循环**：限制最大工具调用轮数（默认 10 轮），超限强制返回

---

### Q5：LangGraph 和 LangChain 的区别？为什么选 LangGraph？

**回答方向**：状态图 vs 链式调用

**答案要点**：

| 维度 | LangChain (Chain) | LangGraph (Graph) |
|------|-------------------|-------------------|
| **执行流** | 线性链，顺序执行 | 有向图，支持分支/循环/条件路由 |
| **状态管理** | 简单传递 | 内置 State 持久化，随时读写 |
| **循环支持** | 不支持 | 原生支持循环（工具调用→LLM→再调用） |
| **适用场景** | 简单 RAG、QA 流程 | 复杂 Agent 工作流、多轮工具调用 |

> **选 LangGraph 的原因**：Agent 需要循环判断"是否需要继续调工具"，这个条件路由 LangChain 的 Chain 很难表达，而 LangGraph 的 StateGraph 原生支持。

## 二、RAG 相关问题（4 问）

### Q6：为什么不用 Fine-tuning 而用 RAG？

**回答方向**：更新频率 + 成本 + 灵活性

**答案要点**：

| 对比项 | Fine-tuning | RAG |
|--------|:----------:|:---:|
| **更新成本** | 每次新文档需重新训练（数小时~数天） | 上传文档即可实时生效（数秒） |
| **计算资源** | 需要 GPU，成本高 | 仅需 Embedding API，成本极低 |
| **知识粒度** | 模型记忆，不可控 | 可精确控制检索哪些文档 |
| **准确性** | 可能遗忘或幻觉 | 基于原文检索，可溯源 |
| **适用场景** | 模型行为调整（风格、输出格式） | 知识库动态更新（运维文档、操作手册） |

> **企业运维文档频繁更新（新版本部署、变更记录），RAG 可以做到"上传即用"，Fine-tuning 完全跟不上这个节奏。**

---

### Q7：Embedding 模型怎么选的？向量维度为什么是 128？

**回答方向**：兼容性 + 降级方案

**答案要点**：

1. **主方案**：使用与 LLM 相同 API 端点的 Embedding 模型（如 `text-embedding-ada-002`）
2. **降级方案**：API 不可用时使用固定向量（128 维全 1 向量），保证系统不中断
3. **维度选择**：
   - 1536（OpenAI Ada-002）— 生产环境
   - 128 — 降级方案维度，足够区分文档类别
   - 通过配置 `EMBEDDING_DIMENSION` 灵活切换

---

### Q8：如何避免 RAG 产生的幻觉？

**回答方向**：检索质量 + Prompt 约束 + 引用溯源

**答案要点**：

1. **检索质量保证**：
   - 文档分割（500 字符 + 50 重叠），确保语义完整
   - 余弦相似度搜索（top_k=3），多片段投票
   - 相似度阈值过滤（低于 0.7 的结果丢弃）
2. **Prompt 约束**：
   - System Prompt 明确要求：仅基于提供的上下文回答
   - 如果上下文不足以回答问题，必须说"根据现有知识库无法确定"
3. **引用溯源**：
   - 回答中可标注信息来源（文档标题、片段位置）
   - Trace 面板展示 Agent 执行链路，可溯源

---

### Q9：知识库的向量存在哪里？为什么不直接用 Pinecone 之类的向量数据库？

**回答方向**：架构简洁 + 数据安全 + PostgreSQL 扩展

**答案要点**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| **Pinecone / Milvus** | 专业向量检索、高性能 | 额外服务、运维复杂、成本高 |
| **pgvector（本项目）** | 无需额外服务，数据和应用同库 | 大规模（>100 万条）检索性能下降 |

> **选择 pgvector 的原因**：
> 1. 企业运维文档规模有限（几千~几万条），pgvector 完全够用
> 2. 减少外部依赖，降低部署复杂度（一个 PostgreSQL 搞定关系+向量）
> 3. 数据与应用同库，事务一致性天然保证
> 4. 如果规模增长，可随时切换到专业向量数据库，接口抽象层已预留

## 三、Kubernetes 相关问题（3 问）

### Q10：Agent 如何发现 Pod 异常？

**回答方向**：kubectl 工具链 + LLM 分析

**答案要点**：

1. **获取状态**：`kubectl_get_pods(namespace="production")` 获取 Pod 列表和状态
2. **筛选异常**：LLM 识别非 Running 状态的 Pod（CrashLoopBackOff、Error、OOMKilled）
3. **深度诊断**：自动调用 `kubectl_describe_pod()` 查看事件 + `kubectl_logs()` 查看日志
4. **根因判断**：LLM 综合分析状态码、事件信息和日志内容，给出故障原因

---

### Q11：K8s 功能的安全权限怎么设计的？

**回答方向**：双开关 + 最小权限

**答案要点**：

1. **功能开关**：`KUBERNETES_ENABLED=false`（环境变量），默认不启用
2. **操作开关**：`KUBERNETES_ALLOW_RESTART=false`，重启等危险操作独立控制
3. **工具分类**：
   - 读操作（get/list/describe）— 启用即可
   - 写操作（restart/delete）— 需额外开启 allow_restart
4. **kubectl 上下文**：使用配置的 kubeconfig，不额外授予集群权限

---

### Q12：如何处理大规模的 K8s 集群（100+ Node）？

**回答方向**：分页 + 过滤 + 异步

**答案要点**：

1. **命名空间隔离**：按命名空间查询，避免全量拉取
2. **LLM 语义过滤**：Agent 先理解用户关注的维度（如"出问题的 Pod"），再针对性调用
3. **异步执行**：长时间查询通过 WebSocket 流式返回，不阻塞 UI
4. **扩展方案**：如果集群规模极大，可引入缓存层（Redis）缓存 Pod 状态，减少 kubectl 调用频率

### Q15：为什么选择 FastAPI 而不是 Django/Flask？

**回答方向**：异步支持 + 性能 + 类型安全

**答案要点**：

| 维度 | FastAPI | Django | Flask |
|------|:-------:|:------:|:-----:|
| **异步原生** | ✅ async/await | ⚠️ 3.0 后支持 | ❌ |
| **自动 API 文档** | ✅ Swagger + ReDoc | ❌ | ❌ |
| **Pydantic 校验** | ✅ 原生集成 | ❌ 需 DRF | ❌ |

| **轻量级** | ✅ | ❌ 重量级 | ✅ |

> **选 FastAPI 的原因**：项目需要 WebSocket 实时通信（Agent 轨迹推送）、异步工具调用（SSH/Docker/K8s 并发执行），FastAPI 的 async 原生支持 + 自动 Swagger 文档 + Pydantic 校验，是 AI Agent 后端的最佳选择。

## 五、架构相关问题（4 问）

### Q17：如果支持 1000 台服务器，现在的架构有什么问题？怎么改？

**回答方向**：识别瓶颈 + 给出方案

**答案要点**：

**当前架构瓶颈**：

| 瓶颈 | 原因 | 影响 |
|:----:|------|------|
| **单进程 Agent** | LangGraph 在单进程中运行 | 无法并发处理大量请求 |
| **SQLite 并发限制** | 开发环境使用 SQLite | 读写锁冲突 |
| **同步 SSH 调用** | 每个 SSH 连接阻塞线程 | 大批量巡检耗时过长 |
| **无缓存** | /api/server/status 每次实时采集 | 高频查询压力大 |

**改造方案**：

| 改造项 | 方案 | 优先级 |
|--------|------|:------:|
| **数据库** | 切换到 PostgreSQL（已支持） | 🔴 高 |
| **Agent 并发** | 引入 Celery / 异步任务队列处理长时间 Agent 任务 | 🟡 中 |
| **SSH 连接池** | 使用 paramiko 的 Transport 池化复用连接 | 🟡 中 |
| **指标缓存** | Redis 缓存系统指标（5s TTL） | 🟢 低 |
| **水平扩展** | 多实例部署，Nginx 负载均衡 | 🟢 低 |

### Q18：RAG 知识库如果扩展到 10 万份文档，性能会下降吗？

**回答方向**：pgvector 限制 + 优化方案

**答案要点**：

**问题**：pgvector 在 10 万级文档（假设每份 20 个 chunk = 200 万向量）时，全表余弦相似度扫描性能显著下降。

**优化方案**：

| 方案 | 效果 | 实现难度 |
|------|:----:|:--------:|
| **IVFFlat 索引** | 检索速度提升 10-100 倍 | 🟢 低（SQL 加索引） |
| **HNSW 索引** | 检索速度提升 100+ 倍 | 🟢 中（pgvector 0.5+） |
| **文档预过滤** | 先根据标签/类别缩小检索范围 | 🟢 低 |
| **切换到 Milvus** | 专业向量数据库，支持百亿级 | 🟡 中（接口已抽象） |

### Q19：LLM 调用成本是多少？如果每天 1000 次调用怎么办？

**回答方向**：成本量化 + 优化策略

**答案要点**：

**当前成本估算**（以 DeepSeek V4 Flash 为例）：

| 场景 | Token 消耗/次 | 成本/次 | 日均 1000 次成本 |
|:----:|:-----------:|:-------:|:---------------:|
| 简单问答 | ~500 tokens | ~¥0.001 | ~¥1 |
| 工具调用（1 轮） | ~2000 tokens | ~¥0.004 | ~¥4 |
| 多步骤（3 轮） | ~5000 tokens | ~¥0.01 | ~¥10 |

**优化策略**：

| 策略 | 说明 | 效果 |
|------|------|:----:|
| **缓存常见问题** | 高频问题（如"检查服务器状态"）缓存回答 | 减少 30% 调用量 |
| **精简历史消息** | 只保留最近 5 轮，减少 Token 消耗 | 减少 20% Token |
| **使用更小模型** | 简单查询用轻量模型，复杂任务用主力模型 | 减少 50% 成本 |
| **本地 LLM** | 部署 ollama 本地模型处理简单任务 | 零成本 |
